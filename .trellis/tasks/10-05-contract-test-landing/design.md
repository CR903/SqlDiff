# design.md — 契约落地（父任务）

## 边界

父任务**不承担实现**，只 owns 三件事：需求集、任务地图、最终集成复核。两条实现线在子任务里独立完成。

```
父 10-05-contract-test-landing
├── A 10-05-unit-test-gap-landing      纯函数/主进程契约测试 → vitest
└── B 10-05-export-e2e-landing          §11.1 保密边界 + 导出契约 + UI E2E → vitest + e2e
```

## 为什么是两条线而不是一个

它们的**验证成本、失败模式、运行依赖完全不同**：

| | 子任务 A | 子任务 B |
|---|---|---|
| 验证方式 | `vitest`，秒级 | `vitest` + Playwright，真机 ~30s/项 |
| 外部依赖 | 无 | MySQL 可达（`.115` / `.84`） |
| 失败含义 | 契约理解错了 | 可能是 DB 不可达，也可能真回归 |
| 是否需真机 | 否 | UI 层需要 |

放一起会让 A 的秒级反馈被 B 的真机耗时拖住，且 B 的环境问题会污染 A 的失败信号。分开后 B 若因 DB 不可达而失败，A 依然是可信的绿灯。

## 共同的测试哲学（本任务的"契约测试"定义）

补的不是"覆盖率数字"，而是**契约的可执行表述**。三类：

### 一、守卫函数的判别矩阵

`isNodeMeta` / `isHistoryEntry` 这类反序列化守卫，真正的契约是**哪些形状被接受、哪些被拒绝**。测试要逐字段打：缺 `id`、类型错、`ssh` 不是 record、数组而非对象……而不是只测一个 happy path。

理由：守卫的作用是在 IPC / 文件边界**挡住坏数据**。只测 happy path 等于没测它的本职。

### 二、注入防线的边界输入

`escapeDataIdent` 的契约是"标识符里的反引号被加倍，从而无法逃逸出反引号包裹"。测试要覆盖：含反引号、连续反引号、空串、非字符串输入。

理由：这是唯一一道把表名/列名送进 SQL 前的防线。它的失效是**静默的注入**，不会被任何现有断言捕获。

### 三、不可变性质（property-like assertion）

§11.1 的"导出物不含凭据"不是某个函数的行为，而是**跨越序列化 + 渲染 + 写盘三个环节后仍成立的不变量**。所以测试要构造含凭据的输入、走完整导出链、对产物断言——而不是断言某个函数"没有引用某个字段"。

理由：字段名黑名单挡不住值泄漏（比如密码被拼进 SQL 字面量或 recommendation 文本）。

## 关键权衡：子任务 B 的 UI 层怎么测

### 约束的来源

`导出 Preflight 报告` 按钮读的是 renderer 的 React state `lastPreflightResult`（`App.tsx:2353`）。而现有真机 spec 全部走 `page.evaluate(() => api.preflight.run(...))` —— **API 直调不会设这个 state**。所以 API 直调无法验证 UI 层。

而 `canRunPreflight` 的前置条件（`App.tsx:673`）是：**真实比较（非 demo）+ 至少 1 条表级 DDL 项**。这意味着要驱动 UI，必须先做一次**真实比较**。

### 两条路与取舍

| | 真机 UI 全链路（选定） | env 门控测试 seed（被否） |
|---|---|---|
| 产品代码改动 | **零** | 需给 renderer 加 seed 入口 |
| 产物 | 真实 compare → 真实 preflight → 真实 3 文件 | 构造的 report → 真实 3 文件 |
| 耗时 | ~30s/项 | ~5s/项 |
| 默认 harness | 不跑（开关门控） | 跑 |
| 依赖 | MySQL 可达 | 无 |

选真机全链路（D2）。**接受的代价必须写明**：回归价值依赖开关是否打开。这是这个选择的真实成本，不粉饰。

### 双库 fixture 是必需的，且一举两得

Preflight 导出需要真实比较，真实比较需要 **A 和 B 两个数据库**且产生表级 DDL 差异。

关键收益：**同一次比较同时满足两个导出**。`导出审查报告` 需要 `lastCompareRequest`（比较产物），`导出 Preflight 报告` 需要 `lastPreflightResult`（比较后跑的 preflight）——都来自这一次比较。这正好对上 `frontend/quality-guidelines.md:69` 的"keep both in the same CDP harness run"要求。

## 漂移问题的处理方式

本任务规划期间连续发现 **4 处 spec 漂移**（§14.10 follow-up 未回填、`schemaVersion` 停在 v1、导出文件数 2 vs 3）。这不是巧合，是同一类：

> **任务新增能力时只更新自己那一节，交叉引用留旧。**

处理原则：**发现即修，但区分"待办清单"与"历史陈述"**。
- §14.10 Follow-up 是活清单 → 回填（`ec9bd1c`）
- §14.9 回滚 是历史陈述 → **不改**，改了等于伪造历史

子任务 B 会再验证一次这个分类：§11.1 是活契约（要落测试），不是历史。

## 兼容与回滚

- 两条子任务都是纯增量（新增测试文件），产品代码零改动 → 回滚就是删测试文件
- 子任务 B 的真机 fixture 走既有 `e2e/fixtures/mysql-fixture.ts` 模式，cleanup 沿用既有约定（`finally` 删库）
- 无迁移动作，无兼容性风险

## 权衡记录

**为什么不并行 dispatch**：两条线共享 `tests/` 目录与 vitest 进程，并行会让"748 → N 项"的计数难以核对（同时改文件可能冲突）。子任务 A 先跑（快、稳），B 后跑（慢、依赖环境），父任务最后做一次全量复核。
