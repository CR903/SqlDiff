# 产品可扩展性与需求路线图

## Goal

基于当前 SqlDiff 桌面版的真实能力、代码边界、用户流程和可验证证据，评估产品下一步可扩展的方向，挖掘高频/高价值但尚未满足的需求，并形成可排序、可分阶段、可验证的产品路线图。

本任务交付的是研究与决策材料，不直接实现功能。

## Background

- 当前产品是 Electron + Vite + React + TypeScript 桌面应用，核心价值是 MySQL 双库结构/数据只读对比、差异 SQL 预览与导出。
- 已有能力包括节点库、safeStorage/Vault、直连与单跳 SSH、A/B 对比、结构与数据差异、过滤/复制/导出、历史记录、DBeaver 拓扑导出和双端打包。
- 产品明确不做自动执行 SQL；`mysqldiff/` 是只读历史兼容实现，不能作为新功能的随意修改目标。
- DataGrip 导出、真实目标数据库验证、签名公证、自动更新等仍是明确的后续/环境受限事项。
- 现有资料包含产品 PRD、历史任务、代码规范、E2E 报告以及 DBeaver/DataGrip 格式研究；新路线图必须区分事实、推断和待验证假设。

## In Scope

1. **能力地图**：盘点当前用户任务、核心对象、连接/安全/数据边界和已实现能力。
2. **问题与需求挖掘**：从用户工作流、失败场景、运维/开发痛点和现有工具缺口中提炼需求假设。
3. **可扩展方向**：至少比较数据库覆盖、协作/团队、审查发布、自动化观测、迁移/转换、开发者体验等方向。
4. **技术与产品可行性**：评估 Electron 主进程/共享核心/renderer 边界、数据规模、部署形态、安全与兼容性成本。
5. **优先级路线图**：用价值、频次、差异化、实现成本、风险和依赖排序，给出近期/中期/远期阶段。
6. **验证计划**：为高优先级假设设计用户访谈、可用性测试、fixture/性能实验或 MVP 验证，不把猜测当作需求事实。
7. **后续 backlog**：将结论拆成可独立验收的候选任务，并明确 DataGrip 等已存在阻塞项与新产品方向的关系。

## Out of Scope

- 本任务不实现新功能、不改产品代码、不新增数据库驱动。
- 不在没有证据时给出市场规模、收入预测或“用户一定需要”的结论。
- 不把自动执行 SQL、云端托管、团队权限或 AI 功能默认列入 MVP；如评估为候选方向，必须标为假设并给出验证门槛。
- 不修改 `mysqldiff/` 或将旧 CLI 当作新架构的默认实现路径。

## Evaluation Dimensions

每个候选方向至少按以下维度评估（1-5 分，并给出证据/假设标记）：

- 用户价值与问题频率
- 与现有能力的复用程度
- 差异化与竞争窗口
- 技术复杂度和交付成本
- 安全、隐私和运维风险
- 对 MySQL-only/桌面-only 假设的突破程度
- 可验证性（能否用小实验验证）
- 对长期平台化的贡献

## Deliverables

- `research/`：代码事实、用户/竞品证据、技术扩展性调查；每条结论标注来源和置信度。
- `roadmap.md`：能力地图、需求假设、候选方向评分矩阵、取舍理由、阶段路线图、风险与下一步实验。
- 最终给出一个推荐的近期重点和最多两个备选重点，避免无边界扩张。

## Acceptance Criteria

- [x] AC1 路线图明确列出当前已实现能力、明确未实现能力和已知技术债，且每项有代码/任务/报告依据。
- [x] AC2 至少提出 5 个有差异化潜力的扩展方向，并逐一说明目标用户、问题、价值假设、复用点、成本、风险和验证方式。
- [x] AC3 需求分为“已证实事实 / 高价值假设 / 待验证问题”，不以空泛竞品描述替代证据。
- [x] AC4 产出带评分依据的优先级矩阵和近期/中期/远期路线图；明确推荐重点、暂缓项及依赖关系。
- [x] AC5 为推荐方向给出下一步最小验证实验和成功/失败判据，能转成后续 Trellis 任务。
- [x] AC6 明确列出与现有 DataGrip、真实环境验证、签名公证、自动更新等任务的关系，避免重复建设。
- [x] AC7 研究结论不要求改产品代码；文档链接、证据路径和 Git 状态可复核。

## Decision Constraints

- 保持只读和秘密不泄露的产品信任边界。
- 优先深化现有 MySQL 双库对比工作流，再考虑跨数据库或云端形态。
- 任何新方向必须说明是否需要改变 Electron 边界、NodeMeta/CompareResult 契约、数据存储或安全模型。
- 路线图建议应能在 1-2 个小任务内验证，而不是直接承诺大规模平台建设。

## Open Questions to Resolve Through Research

- 目标用户是独立开发者、测试/发布人员、DBA，还是需要审计交付的团队？
- 最大痛点是发现差异、生成安全 SQL、跨环境协作，还是持续回归/发布治理？
- 哪些需求在真实工作流中每周发生，哪些只是技术可行但低频？
- DBeaver/DataGrip 兼容是迁移入口还是长期产品价值？
- 团队协作、CI、审批和审计需求是否值得从桌面单机扩展为本地项目/服务形态？
