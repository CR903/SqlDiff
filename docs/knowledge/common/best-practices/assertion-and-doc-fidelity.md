# 断言与文档事实的保真

两条都来自 `10-05-unit-test-gap-landing`（2026-10-05），都是"写下来的东西比真实情况更可信"造成的返工。

## 一、文档里的事实断言，必须读实现核对后再写

**规则**：PRD / design / spec 里凡是**关于代码行为的陈述**（某函数做什么、几个字段、什么语义），写之前先读实现。凭印象 / 凭记忆 / 凭"这类函数通常这样"写的陈述，大概率是错的。

**这次的实际情况**：三处，全错。

| 写在 PRD 里的 | 实现真相 |
|---|---|
| `clearHistory` "文件存在时删除" | `writeJsonFileAtomic(path, [])` —— **写空数组，不删文件** |
| `isNodeMeta` 是 "9 字段守卫" | 判别 **8 个**字段（`group`/`tags`/`star` 是可选类型字段，不参与判别） |
| `diffTableField` "只补畸形输入不抛" | 解析范围是 `1..len-1`，首行 CREATE 头与末行右括号都不参与 |

**为什么代价高**：错的不是文档本身，而是**下游会照着它写代码**。implement 子代理按 PRD 写断言会写出假红的用例；check 子代理要逐条反查实现才能发现。三个文档错误换来两个子代理的返工。

**怎么防**：写 PRD 时凡是出现「X 是 Y 语义」「X 有 N 个字段」这类句子，先 grep 实现确认；拿不准就写进 PRD 让实现方以实现为准并要求回填勘误（这次 implement 就是这么做的，做得对）。

**配套**：实现方发现 PRD 写错时，**就地改正文档 + 追加勘误留痕**，而不是只在报告里说一句。这样错误留在文档里被修正，而不是留在对话里蒸发。

## 二、安全断言的"等价类"要选对，不能随手放宽

**规则**：给安全函数写断言时，"哪些实现差异算等价"必须有依据。**放宽断言的收益是零，代价是放进一个真错误的实现。**

**这次的实际情况**：`escapeDataIdent` 把标识符里的反引号加倍后用反引号包裹。design 原本论证"将来改用 ANSI 双引号包裹也是合法方案，所以断言不该锁死反引号"。

**这个论证本身是错的**：`ANSI_QUOTES` 模式**默认关闭**。关闭时 `"a"` 在 MySQL 里是字符串字面量，不是标识符 —— 所以默认模式下**反引号是唯一合法的标识符引号**。把断言放宽成"反引号或双引号都算过"，等于给"用双引号包裹标识符"这个**真错误的实现**发通行证。

**通用规则**：断言依赖某个**可切换的运行时模式 / 特性开关 / 兼容层**的行为前，先确认那个开关的**默认值**。默认值决定哪种行为是"正确解法"，哪种是"错误解法"。放宽断言前先问：放宽之后，一个明显错误的实现能不能通过？

**怎么表达**：把这类判断写进测试文件头的注释，并说明"这是刻意锁定，不是遗漏"。否则下一个维护者看到"断言过于贴合实现"，很自然会"顺手"放宽——回到放进错误实现的状态。

## 三、守卫函数的测试要打判别矩阵，不是打快照

**规则**：类型守卫 / 校验函数的契约是**接受 / 拒绝的边界**。测试要逐字段做变异（删除 / 类型错 / 空值），外加结构性用例（非对象 / `null` / 数组 / 嵌套错误）。

**为什么不能只用快照**：快照只能记录一个形状。守卫的职责是**在 IPC / 文件边界挡住坏数据**——只测 happy path 等于没测它的本职。

**必测的两个易漏边界**：
- 唯一带额外约束的字段（如 `id.length > 0`）—— 最容易漏测
- 内部 `isRecord` 显式**排除数组**的那一层（`isRecord` 排 `Array.isArray`）——`{}` / `[]` / `['k']` / `'str'` 四态都要打

**附带好处**：逐字段矩阵会自然暴露"哪些字段其实没被守卫"。这次就发现 `isHistoryEntry` 纳 `id: ''` 而 `NodeMeta.id` 有 `length > 0` 约束——不是 bug（产品路径不可达），但值得显式锁成"接受"并在用例名注明归属，避免后来者误判为漏测。
